# Предметная область и бизнес-правила

Основной документ по предметной области. Если код и этот документ расходятся — сначала договоритесь, что верно, потом правьте оба.

## Глоссарий
| Термин | Идентификатор в коде | Смысл |
|---|---|---|
| Товар | `product` | Позиция номенклатуры с уникальным артикулом (`sku`) и единицей измерения |
| Категория | `category` | Узел дерева категорий; у товара ровно одна категория |
| Поставщик | `supplier` | Организация, от которой приходят партии |
| Партия | `batch` | Конкретная поставка товара: количество, закупочная цена, срок годности |
| Движение | `stock_movement` | Запись журнала: что, сколько, когда, кем и почему изменилось |
| На складе | `on_hand` | Физическое количество товара |
| Резерв | `reserved` | Количество, обещанное под заказ, но ещё не отгруженное |
| Доступно | `available` | `on_hand − reserved` — сколько реально можно обещать/списать |
| Минимальный остаток | `min_stock` | Порог: если `available < min_stock`, товара не хватает |
| Инвентаризация | `stocktaking` | Пересчёт физических остатков и сверка с учётными |

## Роли и права
| Действие | viewer | storekeeper | admin |
|---|:-:|:-:|:-:|
| Просмотр всего (остатки, журнал, отчёты) | ✅ | ✅ | ✅ |

| Управление пользователями | ❌ | ❌ | ✅ |

## Главный принцип: остаток не редактируется руками
Количество товара меняется **только** через запись в журнал `stock_movements`. Нет эндпоинта «установить остаток = N».
Из этого следует: история полная, любое число можно объяснить, расхождения исправляются корректировкой
(`ADJUSTMENT`) — тоже движением. Журнал **append-only**: записи не обновляются и не удаляются.

## Типы движений
У движения два знаковых числа: `quantity_delta` (влияет на `on_hand`) и `reserved_delta` (влияет на `reserved`).

| Тип | `quantity_delta` | `reserved_delta` | `batch_id` | Когда |
|---|---|---|---|---|
| `RECEIPT` | `> 0` | `0` | обязателен | приход партии |
| `WRITE_OFF` | `< 0` | `0` | обязателен | списание (продажа, брак, истёк срок, прочее) |
| `RESERVE` | `0` | `> 0` | `NULL` | создан/расширен резерв |
| `RELEASE` | `0` | `< 0` | `NULL` | резерв отменён, истёк или исполнен |
| `ADJUSTMENT` | `≠ 0` | `0` | обязателен | корректировка по итогам инвентаризации |

Вычисляемые значения по товару:
- `on_hand = SUM(quantity_delta)`; `reserved = SUM(reserved_delta)`; `available = on_hand − reserved`;
- по партии: `batches.qty_remaining` — кэш `SUM(quantity_delta)` по этой партии (обновляется в той же транзакции).

## Сценарии и правила

### 1. Приход (приёмка)
Вход: товар, поставщик, номер партии, количество `> 0`, закупочная цена `≥ 0`, дата прихода, срок годности (необязателен).
1. Создаётся `batch` с `qty_received = qty_remaining = количество`.
2. Пишется `RECEIPT`.
Правила: `(product_id, batch_no)` уникальна; срок годности не раньше даты прихода; нельзя принимать товар от удалённого поставщика.

### 2. Списание (правило FEFO/FIFO)
Вход: товар, количество, причина (`SALE`, `DAMAGE`, `EXPIRED`, `OTHER`), комментарий.
1. Заблокировать строку товара (`SELECT … FOR UPDATE`) — все операции с остатками одного товара выполняются по очереди.
2. Проверить `количество ≤ available`, иначе `409 INSUFFICIENT_STOCK`.
3. Выбрать партии с `qty_remaining > 0` в порядке: `expires_at` по возрастанию (**NULL в конце**), затем `received_at`, затем `id`.
4. Списывать жадно: из каждой партии `min(qty_remaining, нужно)`; по **одному** `WRITE_OFF` на каждую затронутую партию.
5. Всё в одной транзакции: либо списалось целиком, либо ничего.

Просроченные партии (`expires_at < сегодня`) при продаже (`SALE`) **пропускаются**; их можно списать только с причиной `EXPIRED`.
Поэтому для `SALE` проверка п. 2 считает остаток только по непросроченным партиям: `количество ≤ (остаток непросроченных партий − reserved)`.
Для прочих причин (`DAMAGE`, `EXPIRED`, `OTHER`) берутся все партии и проверка идёт по обычному `available`.

### 3. Резервирование
Резерв делается **на уровне товара** (не партии): конкретные партии выбираются в момент отгрузки.
- Создание: список позиций (товар, количество), внешний номер заказа (`reference`), срок действия `expires_at` (по умолчанию +7 дней).
  Для каждой позиции: блокировка товара, проверка `количество ≤ available`, иначе `409 INSUFFICIENT_STOCK` и **весь резерв не создаётся**; пишется `RESERVE`.
- Статусы: `ACTIVE → FULFILLED | CANCELLED | EXPIRED` (из конечных статусов выхода нет).
- Отмена/истечение: на каждую позицию `RELEASE` (резерв возвращается в «доступно»).
- Исполнение (отгрузка): на каждую позицию `RELEASE` **и** списание по FEFO (п. 2, причина `SALE`); проверка — количество равно зарезервированному.
- Истечение: периодическая задача (раз в минуту/час) переводит `ACTIVE` с `expires_at < now` в `EXPIRED`.

### 4. Инвентаризация
Статусы сессии: `DRAFT → IN_PROGRESS → CLOSED` (или `CANCELLED` из `DRAFT`/`IN_PROGRESS`).
1. Создание (`DRAFT`): выбор товаров (по категории или все).
2. Старт (`IN_PROGRESS`): для каждой строки фиксируется `expected_qty = on_hand` на этот момент.
   **Пока сессия открыта, движения по её товарам запрещены** (`409 STOCKTAKING_IN_PROGRESS`) — так расхождение считается корректно.
3. Ввод пересчёта: `counted_qty` для строк (можно частями).
4. Закрытие: все строки должны быть заполнены. Для каждой строки `diff = counted_qty − expected_qty`:
   - `diff < 0` — `ADJUSTMENT` с отрицательным знаком, распределяется по партиям по FEFO;
   - `diff > 0` — создаётся корректирующая партия (`batch_no = INV-<id сессии>`, цена — последняя закупочная) и `ADJUSTMENT` с положительным знаком;
   - `diff = 0` — ничего.
5. Резерв не трогаем; если после корректировки `available < 0`, резервы остаются, но товар попадает в отчёт нехватки с пометкой.

### 5. Автоматическое выявление нехватки
У товара: `min_stock` (обязателен, `≥ 0`) и `target_stock` (необязателен; по умолчанию `2 × min_stock`).
- Нехватка: `available < min_stock`.
- Рекомендуемая закупка: `target_stock − available`, округлённая вверх до целого, если единица — штуки.
- Серьёзность: `CRITICAL` — `available ≤ 0`; `WARNING` — иначе.
- В MVP отчёт считается **по запросу** (`GET /alerts/low-stock`). Фоновая проверка с уведомлениями — расширение спринта 4–5.
- Дополнительно: партии, срок годности которых истекает в ближайшие `N` дней (по умолчанию 14) — `GET /alerts/expiring-batches`.

## Единицы и точность
Количества — `NUMERIC(14,3)`; деньги — `NUMERIC(14,2)`. Для штучных товаров (`unit = 'pcs'`) приложение требует целое количество.
Никаких `float` для количеств и денег.

## Удаление данных
- Товар, поставщик, категория с историей **не удаляются**, а архивируются (`is_active = false`).
- Категорию с товарами удалить/архивировать нельзя (`409`).
- Журнал движений не удаляется никогда.

## Что сознательно вне MVP
Несколько складов и ячеек хранения, серийные номера, мультивалютность, интеграции с учётными системами, штрихкоды.
Если понадобится многоскладность, вводится `warehouse_id` в `batches` и `stock_movements` — схема это допускает.
